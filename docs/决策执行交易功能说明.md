## 1. 背景与目标

### 1.1 现状

当前 Trading Agent（PA_Agent）的核心能力是：

```
K 线收盘快照 → 两阶段 AI 分析 → 校验/归一化 → GUI 展示 + 记录落盘 + 软件内持仓跟踪
```

产品规格与交接文档中明确：**不连接券商、不执行真实下单**。软件内 `PositionTracker` 仅根据决策做 `planned → filled → closed` 的状态模拟，用 K 线 high/low 判断触及入场/止盈/止损。

### 1.2 新功能目标

在 **不削弱现有「辅助决策」定位** 的前提下，新增可选的 **决策执行层**：将 Stage 2 通过校验的交易决策，经程序确定性闸门复核后，通过券商接口（首版 MT5）发出真实或模拟订单。

需解决的四个核心问题：

| # | 问题 | 原则 |
|---|------|------|
| 1 | 模型幻觉导致参数填错 | **模型只产出意图，程序决定是否执行、以何价执行** |
| 2 | 分析耗时约 150s，完成后价格已偏离快照 | **执行前刷新 live 市场，按订单类型差异化处理时效** |
| 3 | 网络/券商/状态未知等异常 | **fail-closed、幂等、查单再重试、审计可追溯** |
| 4 | 限价/突破单可能长期未成交，增量分析不知挂单/持仓 | **每轮分析注入真实执行状态，支持撤单/调价/平仓等管理决策** |

### 1.3 非目标（首版不做）

- 不替代完整 Stage1+2 重分析作为「执行前复核」（成本过高）
- 不让模型填写手数/仓位（由程序按风控规则计算）
- 不解析 `invalidation_condition` 自然语言做自动判断（仅结构化硬规则 + 人工审计）
- 不支持多券商并行（接口预留，首版仅 MT5）

## 2. 核心设计原则

### 2.1 分析 ≠ 执行

```
┌─────────────┐    ┌──────────────┐    ┌───────────────┐    ┌─────────────┐
│ K线收盘快照  │ →  │ 两阶段 AI 分析 │ →  │ JsonValidator │ →  │ ExecutionGate│
└─────────────┘    └──────────────┘    └───────────────┘    └──────┬──────┘
                                                                    │
                         ┌──────────────────────────────────────────┤
                         ▼                                          ▼
                  ┌─────────────┐                            ┌──────────────┐
                  │ 拒绝：仅记录 │                            │ BrokerAdapter │
                  │ 通知/软件持仓│                            │ 下单/挂单      │
                  └─────────────┘                            └──────┬───────┘
                                                                    ▼
                                                            ┌──────────────┐
                                                            │ExecutionJournal│
                                                            │ 审计落盘       │
                                                            └──────────────┘
```

- **展示层**（图表 overlay、DecisionPanel、通知）可沿用现有较宽松的校验结果。
- **执行层**（ExecutionGate）标准更严：任一检查失败 → **绝不下单**（fail-closed）。

### 2.2 快照绑定

每笔潜在订单必须绑定：

- `record_id`：`records/pending/{ts}_{symbol}_{tf}.json` 文件名
- `snapshot_ts_local_ms`：提交分析时的快照时间
- `snapshot_bar_count` / 最新已收盘 K 线序号（K1）
- 唯一 `client_order_id = hash(record_id + symbol + timeframe)`，防重试重复下单

### 2.3 执行模式分级（强烈建议分阶段上线）

| 模式 | 说明 | 风险 |
|------|------|------|
| **paper**（纸面/模拟，默认） | 只走 ExecutionGate + 纸面 Broker，不调 MT5 下单 | 低 |
| **confirm**（确认后执行） | Gate 通过后 GUI 弹复核面板，用户一键确认再下单 | 低 |
| **auto**（自动执行） | Gate 通过 + 未超风控限额则自动下单 | 高 |

首版默认 `paper`；`auto` 需显式开启并配置风控参数。

### 3.2 接入点

在 `TwoStageOrchestrator.submit()` 完成 Stage2 校验、`PendingWriter.save_full()`、`PositionTracker.apply_decision()` 之后：

```python
if settings.execution.enabled and settings.execution.mode != "disabled":
  live_ctx = live_market_provider.fetch(symbol, timeframe)
  verdict = execution_gate.evaluate(record, live_ctx)
  if verdict.approved:
    if settings.execution.mode == "auto":
      execution_engine.execute(verdict.intent, live_ctx)
    elif settings.execution.mode == "confirm":
      event_bus.emit(ExecutionReviewRequired(verdict))  # GUI 确认

```

## 4. 问题一：防幻觉与决策一致性

### 4.1 威胁模型

| 幻觉类型 | 示例 | 后果 |
|----------|------|------|
| 价格乱填 | entry 不在依据 K 线极点附近 | 错误挂单 |
| 结构矛盾 | terminal=reject 但 order_type=突破单 | 不该做却做了 |
| 方向矛盾 | Stage1 bullish 却做空且无 node 2.3 | 逆势单 |
| 几何无效 | 做多但 sl > entry > tp | 券商拒单或即时亏损 |
| 方程不通过 | RR < 下限仍下单 | 期望值为负 |

### 4.2 多层闸门（执行专用，严于展示）

#### 层 1：校验链全通过（硬前提）

- `JsonValidator.validate("stage2")` 返回 `Ok`，且无未解决的 category `c` 级硬错误（可配置：strict 模式下 category `d` 自动修复项也拒绝执行）
- Stage1 `gate_result == proceed`（非 wait/unknown 短路）
- 非 `gate_shortcircuited` 的 Stage2 stub

#### 层 2：结构一致性（程序确定性）

| 检查项 | 规则 |
|--------|------|
| terminal vs order_type | `terminal.outcome == trade` ⟺ `order_type ∈ {限价单, 突破单, 市价单}` |
| §10.3 交易者方程 | trace 中 10.3=是；与 `trade_metrics` 复核一致 |
| §14 禁止清单 | 任一 §14 answer=是（且非误填否认短语）→ 拒绝 |
| 持仓管理 vs 新开仓 | 已有 `filled` 持仓时，仅 `position_action` 管理语义可改 TP/SL/平仓，不静默开新仓 |

#### 层 3：价格锚定到快照 K 线

决策字段（已有）：

- `entry_basis_bar`：如 `K2`
- `entry_basis_extreme`：`high` / `low`
- `entry_rule`：文字说明（审计用）

程序在 **分析快照** 上重算期望价：

```
突破单做多：expected_entry = basis_bar.high + 1_tick
突破单做空：expected_entry = basis_bar.low  - 1_tick
限价单：expected_entry 应在 basis 极点或结构位（首版：与 entry_price 偏差 ≤ max_anchor_deviation_ticks）
```

若 `|entry_price - expected_entry| > max_anchor_deviation_ticks` → **拒绝执行**（首版不建议自动修正后下单，避免掩盖幻觉）。

止损/止盈：

- 做多：`stop_loss < entry < take_profit`
- 做空：`take_profit < entry < stop_loss`
- 复用 `compute_risk_reward()`；`ratio` ≥ `min_risk_reward_ratio(decision_stance)`

#### 层 4：置信度与信号质量门槛（可配置，默认严于 GUI）

| 字段 | 保守默认（执行） | 说明 |
|------|-----------------|------|
| `trade_confidence` | ≥ 60 | 展示可更低 |
| `estimated_win_rate` | 必填 0–100 | 且 `passes_trader_equation()` |
| `entry_bar.freshness` | 必须 `fresh` | `stale`/`invalid` 拒绝 |
| `entry_bar.follow_through` | 不得 `false`（非 pending 入场） | 与 validator 一致 |
| `bar_analysis.signal_bar.quality` | 不得 `invalid`（非 planned_without_signal） | 见 `json_validator` |

#### 层 5：幂等与重复决策

- 同一 `record_id` 只允许一次成功 `place`（journal 查重）
- 同一 `symbol|timeframe` 已有券商挂单/持仓时，新开仓需显式策略（默认：拒绝并提示先处理现有仓）

### 4.3 人机复核（confirm 模式）

Gate 通过后，GUI 展示 **程序复核摘要**（非仅 AI 原文）：

- 快照 K1 时间、分析耗时
- 锚定重算价 vs 模型 entry 偏差（tick）
- 即时 RR、交易者方程、trade_confidence
- 执行将使用的订单类型（LIMIT/STOP/MARKET）与 live 价关系
- 拒绝原因列表（若有 warnings 但不阻断，需标注）

用户确认后才调用 `BrokerAdapter.place()`。

## 5. 问题二：分析延迟与价格偏差

### 5.1 问题本质

- 用户通常在 **K 线收盘后** 提交分析；快照中 K1 = 最新已收盘棒。
- 两阶段 LLM 约 **150s**；完成时：
  - **15m 周期**：通常仍在同一根 forming bar 内（`bars_since_snapshot == 0`），但价格可能已明显移动。
  - **5m 及更短周期**：可能已有 **1 根新收盘 K 线**（`bars_since_snapshot >= 1`），分析结构可能已过期。

> **不能接受**：把 150s 前的 `entry_price` 不经复核直接送券商。

### 5.2 执行前 Live 市场上下文

```python
@dataclass
class LiveMarketContext:
    symbol: str
    timeframe: str
    bid: float
    ask: float
    last_closed_bar: KlineBar       # 当前 K1（已收盘）
    forming_bar: KlineBar | None  # 未收盘棒（若有）
    bars_since_snapshot: int      # 快照后新增已收盘棒数量
    elapsed_ms: int               # 自 snapshot_ts 起经过时间
    spread: float                 # ask - bid
```

由 `LiveMarketProvider` 在 Gate **之后、下单之前** 拉取（MT5：`symbol_info_tick` + `copy_rates`）。

### 5.3 时效性（Staleness）规则

| 条件 | 默认动作 | 可配置 |
|------|----------|--------|
| `elapsed_ms > execution_ttl_ms` | 拒绝，`reason=stale_timeout` | 默认 300000（5 分钟） |
| `bars_since_snapshot >= 1` | 拒绝，`reason=stale_new_closed_bar` | 可改为仅 warn（不推荐 auto） |
| 价格触发 invalidation 硬规则 | 拒绝，`reason=setup_invalidated` | 见 §5.5 |
| Gate 通过但 live 滑点超限 | 拒绝，`reason=slippage_exceeded` | 见 §5.4 |

**推荐默认（15m + 150s）**：

- `bars_since_snapshot == 0` → 允许进入订单类型细分逻辑
- `bars_since_snapshot >= 1` → **自动执行拒绝**；paper/confirm 可降级为「仅展示 + 通知重新分析」

### 5.4 按订单类型差异化

#### 突破单

| Live 价格相对触发价 `entry` | 动作 |
|----------------------------|------|
| 未触及（做多：live < entry；做空：live > entry） | 挂 **STOP** 单（`BUY_STOP` / `SELL_STOP`），触发价 = 校验后的 `entry` |
| 已突破，偏离 ≤ `max_slippage_ticks` | 可配置：① 拒绝 `missed_breakout` ② 转市价（需重算 RR） |
| 已突破，偏离 > `max_slippage_ticks` | 拒绝，`reason=missed_breakout_chase_denied` |
| 突破后回落、结构失效（硬规则） | 拒绝 |

#### 限价单

| Live 价格相对 `entry` | 动作 |
|----------------------|------|
| 未触及有利侧 | 挂 **LIMIT** 单 |
| 在 entry ± `max_slippage_ticks` 内 | 可立即 LIMIT 成交或市价（配置） |
| 已穿过 entry 向 **不利** 方向 | 拒绝（挂单无意义或更差） |
| 已穿过 entry 向 **有利** 方向 | 拒绝 `missed_entry`（不追单，除非显式开启追单且 slippage 内） |

#### 市价单

| 规则 | 说明 |
|------|------|
| **不使用** 快照 `entry_price` 作为成交价 | 以 `ask`（做多）/ `bid`（做空）为基准 |
| 下单前重算 RR | 用 live 价替代 entry；若 RR < 下限 → 拒绝 |
| 时效最严 | 若 `entry_bar` 对应 K 线已不是当前 K1 → 默认拒绝 |
| 滑点保护 | `max_slippage_ticks`；MT5 可用 deviation 参数 |

### 5.5 失效条件（结构化硬规则，首版）

`invalidation_condition` 文本字段 **不作为自动执行依据**（避免 NLP 二次幻觉）。首版实现以下确定性规则：

| ID | 规则 | 做多示例 |
|----|------|----------|
| INV-1 | 快照后新增已收盘 K 线收盘价跌破 `signal_bar` 低点 | 空头突破信号失效 |
| INV-2 | `bars_since_snapshot >= 1` 且新 K1 为反向强棒（实体 > 0.5 × ATR14） | 结构被逆转 |
| INV-3 | Live 价已触及原 `stop_loss` 一侧（未挂单即已止损区） | 不应再入场 |

后续可扩展 INV 规则表，均需 **程序可验证、可单测**。

### 5.6 不调用完整重分析的原因与替代

完整 Stage1+2 再跑一遍约 150s+，失去执行意义。

**替代方案**（按成本递增）：

1. **确定性复核**（首版）：`stale_check` + INV 规则 + 价格几何
2. **轻量节点引擎**（P2）：仅跑 `decision_nodes` 子集 + 新 K1 OHLC
3. **用户触发重分析**（默认路径）：跨棒拒绝时通知「分析已过期，请重新分析」

## 6. 问题三：异常处理

### 6.1 异常分类

| 阶段 | 类型 | 示例 | 处理策略 |
|------|------|------|----------|
| 分析期 | 校验失败 | JSON category c | 已有逻辑；不进入执行 |
| 执行前 | Gate 拒绝 | 锚定偏差、stale | 写 journal + 通知；不下单 |
| 券商可恢复 | 瞬态错误 | MT5 未连接、timeout | 有限重试 + **先查单再重发** |
| 券商明确拒绝 | 业务错误 | 保证金不足、无效价、市场关闭 | 不重试；通知 + journal |
| 状态未知 | 请求无响应 | 网络中断 | **禁止盲目重发** → query 挂单/持仓 |
| 运行期 | 成交/平仓 | 触及 SL/TP | 券商 SL/TP 或程序轮询；更新 Tracker |

### 6.2 重试与幂等

```
place_order(client_order_id)
  → success: journal.record_placed(ticket)
  → timeout/unknown:
       tickets = broker.query_by_client_id(client_order_id)
       if tickets: journal.reconcile(tickets)
       else if retries < max_retries: backoff retry
       else: journal.record_error("unknown_state")
  → explicit_reject: journal.record_rejected(reason), no retry
```

`client_order_id` 写入 MT5 comment 或 magic number 编码，便于回查。

### 6.3 风控熔断（必须有）

| 配置项 | 说明 |
|--------|------|
| `execution_enabled` | 总开关 |
| `max_orders_per_day` | 当日最大下单次数 |
| `max_open_positions_per_symbol` | 单品种最大持仓 |
| `max_risk_per_trade_pct` | 单笔风险占权益 %（用于算手数） |
| `daily_loss_limit_pct` | 当日亏损达限 → kill switch |
| `default_volume` / `volume_mode` | 固定手数 vs 按风险计算 |

**手数永远由程序计算**，模型不输出 volume。

Kill switch 触发后：拒绝一切新单、通知、写 journal、GUI 显著提示；需人工重置或次日自动解除（可配置）。

## 7. 挂单、持仓与增量分析

限价单、突破单可能在数根 K 线内都不成交；同时用户会开启 **增量分析**（`keep_analysis` 或手动「增量分析」），每根新 K 线收盘后再跑一轮 Stage1+2。若模型不知道当前仍有挂单或持仓，可能：

- 重复给出同向新开仓计划（与现有单冲突）；
- 该撤单时仍假设「无单」；
- 该移动止盈止损或提前平仓时，只输出「不下单」而无结构化动作。

本节定义：**如何把执行状态喂给 LLM**，以及 **如何把管理类决策落到券商**。

### 7.1 现状（软件层已有部分能力）

| 能力 | 实现位置 | 说明 |
|------|----------|------|
| 软件内状态机 | `positions/tracker.py` | `planned`（计划单/挂单）→ `filled`（持仓）→ `closed` |
| Stage2 持仓注入 | `prompt_assembler._render_active_position()` | 有 `active_position` 时写入 Stage2 user prompt |
| 持仓管理枚举 | `positions/decision_fields.py` | `position_action`：`持有` / `调整` / `平仓` |
| Schema | `ai/prompts/schemas.py` | `不下单 + 调整` 允许改 TP/SL；`平仓` 三价全 null |
| 计划单撤销 | `PositionTracker._manage_existing()` | `planned` + 新决策 `order_type=不下单` → 清除计划单 |
| 增量分析 | `analysis_history.py` + `build_incremental_stage1()` | 基于上轮 record 只分析新增 K 线 |

**缺口（执行功能需补齐）**：

1. **券商挂单**与 `PositionTracker` / `positions.json` 可能不一致，需统一为 `PortfolioContext`。
2. **增量 Stage1** 目前不注入挂单/持仓，模型在诊断阶段看不到执行状态。
3. **计划单调价**（改 entry/TP/SL）无显式 `position_action`，靠「同向新三价」隐式表达，执行层需定义改单规则。
4. **撤单** 仅靠 `不下单` 隐式触发，建议增加显式 `position_action=取消挂单`（或等价字段）便于审计与 Gate 区分「无操作」与「主动撤单」。
5. 实盘 **modify / cancel / close** 需 `ExecutionEngine` 实现，不能只做软件 `PositionStore`。

### 7.2 统一上下文：PortfolioContext

每次分析（全量或增量）开始前，由程序组装 **单一真相源**（提交分析前刷新一次）：

```python
@dataclass
class PendingOrderView:
    client_order_id: str
    broker_ticket: int | None      # 实盘有；纸面可为 null
    source_record_id: str          # 哪次分析产生的
    order_type: str                # 限价单 / 突破单
    order_direction: str
    entry_price: float
    take_profit_price: float | None
    stop_loss_price: float | None
    placed_at_ms: int
    bars_waiting: int            # 挂单后经过的已收盘 K 数

@dataclass
class OpenPositionView:
    broker_ticket: int | None
    order_direction: str
    volume: float
    fill_price: float
    take_profit_price: float | None
    stop_loss_price: float | None
    filled_at_ms: int
    unrealized_pnl: float | None   # 可选，来自 MT5

@dataclass
class PortfolioContext:
    symbol: str
    timeframe: str
    pending_orders: list[PendingOrderView]   # 首版每 key 最多 1 笔，结构预留列表
    open_position: OpenPositionView | None
    sync_ts_ms: int
    sync_source: Literal["tracker", "broker", "merged"]
```

**同步策略**：

```
分析提交前
  → broker.query_pending() + broker.positions()   # 实盘/纸面 broker
  → PositionStore.get_active()                     # 软件镜像
  → merge：以 broker 为准；漂移写 journal 告警并尝试 reconcile
  → 得到 PortfolioContext
  → 注入 Stage1（增量）与 Stage2 prompt
  → 分析结束后 ExecutionEngine 根据决策 + 同一 context 执行动作
```

### 7.3 注入 Prompt 的规则

#### 7.3.1 Stage 2（延续现有 `_render_active_position`，扩展为 PortfolioContext）

将 `active_position: PositionState` 升级为 `portfolio: PortfolioContext`，prompt 块包含：

| 块 | 内容 |
|----|------|
| 挂单列表 | 类型、方向、挂单价、TP/SL、已等待 K 数、来源 record_id |
| 持仓 | 成交价、当前 TP/SL、浮盈（可选） |
| 任务说明 | 见下表「分析任务优先级」 |

**分析任务优先级**（写入 prompt，减少模型混乱）：

| 当前状态 | 本轮 Stage2 首要任务 | 禁止 |
|----------|---------------------|------|
| 仅有挂单 `planned` | 评估挂单是否仍有效；失效则撤单；有效可微调三价 | 默认同向再开一单 |
| 仅有持仓 `filled` | **持仓管理**（持有/调整/平仓） | 同向重复开仓 |
| 挂单 + 持仓 | 先管理持仓，再评估挂单（通常不应并存，并存时告警） | 同时输出两个新开仓 |
| 皆无 | 正常入场决策 | — |

#### 7.3.2 Stage 1 增量分析（新增）

`build_incremental_stage1()` 的 user prompt 中增加 **简短执行状态摘要**（不必走完整 §12/§13，但模型需知「外面有单」）：

```text
## 当前执行状态（程序同步，非 K 线数据）

- 挂单：1 笔，做多突破单 @ 2344.50，等待 2 根已收盘 K，来源 record xxx
- 持仓：无

阶段一诊断请结合：若新增 K 线已使上述挂单/持仓逻辑失效，在 gate_trace / key_signals 中体现。
```

这样 Stage1 的 `gate_result`、方向判断可与执行状态一致，减少 Stage2 与 Stage1 打架。

#### 7.3.3 与上轮 record 的关系

增量分析已注入上轮 `stage2_decision`（见 `build_incremental_stage1`）。**PortfolioContext 是「地面真相」**，若与上轮决策不一致（例如用户手动在 MT5 撤单），以 `PortfolioContext` 为准，并在 prompt 中注明：

> 「上轮分析建议挂突破多单，但当前券商侧无挂单（可能已成交/已撤/同步延迟）。」

### 7.4 决策语义扩展（Stage2 JSON）

在现有 `position_action` 基础上，区分 **持仓** 与 **挂单** 管理：

| 场景 | order_type | position_action | 程序解释 |
|------|------------|-----------------|----------|
| 无单，正常不下单 | 不下单 | `null` | 无执行动作 |
| 撤销挂单 | 不下单 | **`取消挂单`**（拟新增） | `broker.cancel(ticket)`；清 `planned` |
| 挂单仍有效，不动 | 不下单 | **`维持挂单`**（拟新增）或省略 | 无 broker 操作；可选更新 watch_points |
| 挂单调价 | 限价单/突破单 | **`调整挂单`**（拟新增） | `entry/tp/sl` 有变化 → `broker.modify`；须通过 Gate |
| 持仓不动 | 不下单 | `持有` | 无 broker 操作 |
| 持仓改 TP/SL | 不下单 | `调整` | `broker.modify_position` 或 SL/TP 单 |
| 持仓平仓 | 不下单 | `平仓` | `broker.close_position` |
| 方向反转 | 反向下单类型 | `null` | 先平后开（已有 tracker 逻辑，执行层需对接 broker） |

**兼容性**：未填新枚举时，保留现有行为：

- `planned` + `order_type=不下单` → 视为撤单（现有 `PositionTracker`）；
- `planned` + 同向新三价 → 视为改单（需执行层显式实现）；
- `filled` + `position_action` → 沿用现有 schema。

`position_action` 拟扩展 enum（`schemas.py` + `decision_fields.py`）：

```python
"enum": ["持有", "调整", "平仓", "取消挂单", "维持挂单", "调整挂单", None]
```

校验规则（执行 Gate 附加）：

- `取消挂单` / `维持挂单` / `调整挂单` → 当前 **必须** 存在 `pending_orders`；否则 category c 拒绝执行。
- `调整` / `平仓` / `持有` → 当前 **必须** 存在 `open_position`。
- `调整挂单` 时 `entry_price` 可为新挂单价；须重新过锚定与 RR 检查。

### 7.5 执行引擎：管理类动作（非新开仓）

`ExecutionEngine.apply_management_decision(decision, portfolio)` 在 Gate 通过后：

| 动作 | Broker API（MT5） | 本地 |
|------|-------------------|------|
| 取消挂单 | `order_cancel(ticket)` | `PositionStore.clear_active`；journal `cancelled` |
| 调整挂单 | `order_modify(ticket, price, sl, tp)` | 更新 `PositionState` 三价；journal `modified` |
| 调整持仓 SL/TP | `position_modify` 或先撤后挂 SL/TP | `PositionTracker` upsert |
| 平仓 | `position_close` | `PositionTracker._close` |
| 方向反转 | `close` + `place`（新 client_order_id） | 先关后开 |

**与新开仓 Gate 的区别**：

- 管理类动作 **不做** 「快照锚定 entry」检查（entry 已是历史决策），但 **调整挂单** 的新 entry 仍要做锚定与 RR。
- 管理类 **不做** 150s stale 拒绝（用户意图是管理现有风险），但仍校验价格几何合法。

### 7.6 增量分析下的执行闭环

典型时间线（15m，持续跟踪）：

```
T0  K1 收盘 → 全量分析 → 突破单挂入 @ 2344.50（planned / broker pending）
T1  K2 收盘 → 增量分析（注入：挂单等待 1 根）
      → AI：order_type=不下单, position_action=维持挂单
      → 无 broker 操作
T2  K3 收盘 → 增量分析（注入：挂单等待 2 根，K2 反向强棒）
      → AI：position_action=取消挂单, reasoning=...
      → ExecutionEngine cancel
T3  K4 收盘 → 无挂单 → 正常新入场决策
```

或持仓路径：

```
T0  市价成交 → filled
T1  增量 → position_action=调整, 新 SL/TP → broker modify
T2  增量 → position_action=平仓 → broker close
```

### 7.7 与 ExecutionGate 的协作

| 决策类型 | Gate 重点 |
|----------|-----------|
| 新开仓 | 全文 §4–§5：锚定、stale、RR、幂等（无并发挂单/仓） |
| 取消挂单 | 确认 ticket 存在；无需 RR |
| 调整挂单 | 新三价几何 + 锚定（若改 entry）+ 不扩大风险超配置上限 |
| 调整持仓 | 新 SL 不得立即置于现价错误侧；TP/SL 方向合法 |
| 平仓 | 确认有持仓；可选滑点上限（市价平） |

**并发约束**（建议默认）：每个 `symbol|timeframe` 同时最多 **1 笔挂单 + 1 笔持仓**；超出则 Gate 拒绝新开仓，并 prompt 要求先管理现有单。

```
pa_agent/execution/
├── portfolio_context.py   # 组装、broker↔tracker 合并、prompt 序列化
├── management.py          # 解析 position_action → ManagementIntent
└── ...
```

| 接入点 | 改动 |
|--------|------|
| `MainWindow._begin_submit_analysis` | 提交前 `PortfolioContextBuilder.build(symbol, tf)` |

### 7.9 测试要点

- 有 `planned` 时增量 prompt 含挂单块；模型输出 `取消挂单` → mock broker `cancel` 被调用一次。
- 有 `filled` 时输出 `调整` → TP/SL 变化同步 broker + tracker。
- 有挂单时模型输出同向新开仓 → Gate 拒绝或 normalizer 降级为 `调整挂单`（策略待定，默认 **Gate 拒绝**）。
- broker 无单、tracker 有单 → 同步告警，prompt 标注不一致；不自动新开仓。
- 增量 + `维持挂单`：连续 N 轮无 broker 调用，journal 无重复 cancel。

### 8.3 BrokerAdapter 协议

```python
class BrokerAdapter(Protocol):
    def connect(self) -> None: ...
    def disconnect(self) -> None: ...
    def place(self, intent: ExecutionIntent) -> BrokerOrderResult: ...
    def cancel(self, ticket: int) -> bool: ...
    def modify_order(self, ticket: int, *, price: float | None, sl: float | None, tp: float | None) -> BrokerOrderResult: ...
    def close_position(self, ticket: int, *, volume: float | None = None) -> BrokerOrderResult: ...
    def query_order(self, ticket: int) -> BrokerOrderResult | None: ...
    def query_by_client_id(self, client_order_id: str) -> list[BrokerOrderResult]: ...
    def positions(self, symbol: str | None = None) -> list[BrokerPosition]: ...
```

### 8.4 MT5 订单类型映射

| 决策 order_type | 条件 | MT5 type |
|----------------|------|----------|
| 突破单 | 做多，未触及 | `ORDER_TYPE_BUY_STOP` |
| 突破单 | 做空，未触及 | `ORDER_TYPE_SELL_STOP` |
| 限价单 | 做多，价在 entry 下方 | `ORDER_TYPE_BUY_LIMIT` |
| 限价单 | 做空，价在 entry 上方 | `ORDER_TYPE_SELL_LIMIT` |
| 市价单 | 做多 | `ORDER_TYPE_BUY` |
| 市价单 | 做空 | `ORDER_TYPE_SELL` |

SL/TP 通过 `sl` / `tp` 字段一并提交（`ORDER_FILLING_RETURN` 等 filling mode 按品种配置）。

## 12. 风险与合规提示

- 本功能将真实资金暴露于程序与模型错误风险；**默认关闭**，需用户显式配置。

- 建议模拟账户充分验证后再开 `confirm`/`auto`。
- AGPL-3.0 下若分发含执行模块的修改版，需遵守许可证义务。
